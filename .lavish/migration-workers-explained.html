A beginner-friendly map of the migration system

Fourteen tiny clerks, one API process, one shared ledger.

The “workers” are background loops inside the Rust API. They are not fourteen servers. Each one watches a different kind of migration work, claims a small piece, does it, and writes the result back to PostgreSQL.

14 tasks × 1 API That is the current shape per API process. The three APIs on this Mac are a development API plus two mobile test fixtures.
Start here

What is a worker?

A worker is just a small background loop. It wakes up, asks “is there work for me?”, handles a bounded batch, records what happened, and sleeps again. When there is no work, it does not sit in a separate server waiting for a customer.

Example: admitted-People history

Mobile007 is the mobile feature name. 010d3 is the migration feature name. For this example, the capture worker and admitted-history worker do most of the special work; the other workers keep supporting queues available.

Admin asks for a preview.

The API checks the Organization, source connection, migration workspace, and which People are truly admitted.

Capture stores a safe checkpoint.

The history-capture worker reads qualifying retained source data and stores an encrypted checkpoint. The later import does not need to call the source again.

Admin reviews and confirms.

The Web screen shows counts, held records, and ambiguity. Confirmation is required before facts are written.

One worker claims a small batch.

The admitted-history worker claims up to 50 units with a lease. If another API replica sees the same row, the lease prevents duplicate work.

Facts and provenance are written.

Each result is linked to the correct Person and source identity. Success, hold, or failure is recorded separately.

Cancel and resume stay exact.

Completed facts remain. The unprocessed remainder is recorded, so Resume continues from the right place without re-importing settled work.

The question behind the CPU spike

Could one supervisor wake workers up?

Yes. That would be a different runtime shape, not a change to the migration rules. The database must remain the source of truth even if a supervisor sends wake-up signals.

Current: workers check the ledger today

  • One API process owns the HTTP server and worker tasks.
  • Each worker wakes on a timer, usually once per second or slower.
  • It claims work with a database lease.
  • Simple to run and already implemented.
  • Idle workers create repeated database reads.
vs

Possible later: supervisor + worker process proposal

  • A supervisor watches for new queue work.
  • It sends a wake-up signal to a worker process.
  • The worker still claims from PostgreSQL before doing anything.
  • A slow safety sweep handles missed signals or restarts.
  • Fewer idle reads, but more moving parts to operate.
My recommendation: keep the in-process model for the first production deployment, with one API pod. Before adding multiple API replicas, measure worker and database load. If idle polling is still material, extract one dedicated migration-worker Deployment or add a supervisor with durable wake-up semantics. A notification must be a hint, never the only record of work.
How the supervisor idea would work

Signal first, verify second

The safe design is not “the supervisor tells the worker what is true.” It is “the supervisor says something may have changed; the worker checks the authoritative ledger.”

Bottom line

What should we do?

Now

Run one shared-development API. Stop the two mobile fixture APIs when mobile testing is finished. That immediately removes roughly two redundant copies of the worker set.

Before production has multiple API replicas

Measure database traffic, source rate limits, connection usage, and lease handoff. Decide whether in-process workers remain replicated or move to one dedicated worker Deployment.

If we build the supervisor design

Use PostgreSQL queue rows and leases as the truth. Use notifications only as wake-up hints. Keep a slow safety sweep so a lost signal cannot strand work.
