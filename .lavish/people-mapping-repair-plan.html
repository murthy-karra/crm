Plan for review Existing People first · selected
Your scope choice

Start with People who already exist in CRM—whether they arrived in the first import or a later import. Recovering People that were never imported comes next.

The problem

A missing mapping can hold up an entire update.

A mapping is an approved connection between something in Follow Up Boss and something in CRM. For example, “FUB agent Sam means CRM member Jamie.”

The current refresh uses the choices approved during the original import. An unfamiliar source agent, new source stage, or invalid destination can leave the Person's update on hold.

This plan adds an explicit repair approval. The old import and its original result remain preserved.

What the administrator will see

One choice. A complete preview.

It also works when every update is held.

Start from the blocked preview using “Replace preview with mapping repair.” The old preview is preserved and retired so it cannot execute later. You do not have to confirm a zero-item update first.

Repair can unblock more than the assignment.

The same saved FUB record may contain a new name or phone number. The preview includes every core change, along with any explicit clearing or removal.

Local edits still win protection.

The worker compares CRM with what migration last wrote. If someone changed a relevant field, the whole Person stays held for separate resolution.

Eligible after review

CRM still matches the last migration-written values. The confirmed update can proceed.

The important follow-through

The next refresh remembers the correction.

A successful repair saves the new approval for the exact Person and source key. Otherwise a later refresh could use the old mapping and undo the correction.

Alex + the same source key

The next normal refresh uses Alex's successful repair approval, provided its destination is still valid.

Another Person

Their mapping is unchanged. An approval for Alex does not silently reassign everyone with the same source agent.

Jamie becomes inactive

The update stays held. The system does not silently fall back to an older assignment.

Safe retries

Keep the change and its receipt together.

Each small database transaction saves the Person update, mapping approval, baseline, result and progress together. A baseline is the last set of values migration successfully wrote.

If a worker crashes before that transaction commits, the unit rolls back. If it crashes after commit, another worker reads the saved result and avoids repeating the change.

Cancellation keeps completed work and reports the exact unfinished remainder. Repairing an old hold always gets a new preview.

Proposed first-slice choices

  • Choose an existing CRM stage.
  • Choose an active Organization member, or explicitly choose unassigned.
  • Leave an unresolved mapping visibly held.
  • Keep imported workspaces in admin review.

Existing execution machinery

Extend the two refresh workers already present: one for original-import People, one for later-imported People.

No additional polling loop or worker executable in this slice. The supervisor and production scaling discussion remains a separate architecture task.

Implementation sequence

Build and verify one bounded slice.

  1. Review the contract

    Check approval scope, future-refresh behavior, source ordering and compatibility; accept the implementation proposal.

  2. Backend and database

    Add immutable repair approvals and connect both existing refresh engines to them.

  3. Admin interface

    Held result → choices → complete preview → confirmation → results and recovery.

  4. Prove the failure paths

    Exercise local edits, crashes, duplicate retries, cancellation, tenant isolation and subsequent normal refreshes.

  5. Release when requested

    Deploy a verified compatible build with fresh workload evidence.

Compatibility is part of the work.

Older API or worker builds do not understand repair approvals. The release gate must prevent them from handling an affected workspace, including through an ordinary refresh.

What this first slice leaves for later

Never-imported People; creating stages or members inside repair; forced resolution of local edits; notes/tasks/history mapping repairs; other-family updates; final reconciliation and activation.

What remains before real customer use

Live FUB qualification, customer-data erasure/retention/key readiness, restore proof and production worker reliability retain their own gates.

What is accepted and what is proposed

You selected existing People first. Per-Person mapping persistence, existing-target-only choices, full core re-preview and the new contracts are draft implementation proposals. Independent review and implementation acceptance still follow.
