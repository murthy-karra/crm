01
Core stack

Workspace access and team membership

Membership and session state determine every later journey's authority.

WhoPlatform administrator, Organization admin, two members, and a second Organization.

Starting stateA platform identity and isolated Organizations created through application commands.

  1. 01a

    Open a workspace

    Platform admin creates an Organization → invites its first admin → invitation is accepted → admin invites an agent → agent signs in and reaches Today.

  2. 01b

    Change responsibility and access

    Promote/demote a member → reject removal of the last active admin → deactivate a signed-in member → their next request loses access and realtime disconnects → reactivate → sign in again.

  3. 01c

    Recover and close access

    Revoke/reissue an invitation → old link stays invalid → platform admin restores admin continuity without tenant-data access → logout and sign in as another actor without stale private content.

What must be true at the end

Membership and administrative facts persist; deactivation preserves attributed records; revoked sessions cannot keep reading or writing. A platform administrator never gains CRM access merely from that role.

Failure branches and source anchors

Invitation replay, revoked/expired links, denied member-only/admin-only routes, cross-Organization resource IDs, and retained cache after identity change.

Core stack

Lead arrival, response, and handoff

An Inquiry creates work; contact resolves that work; another Inquiry and reassignment change who must act.

WhoAgents A and B in one Organization; agent C in another.

Starting stateAn operational Organization with default feeds, no saved-list sources or due tasks, and known seeded stages.

  1. 02a

    Work a new lead

    Agent A submits New lead → Person, contact methods, Inquiry, routing, assignment and initial stage appear → Today explains the work → log contact → the inquiry reason clears.

  2. 02b

    Handle a returning lead

    Submit a genuinely new Inquiry with the same contact and a different source → reuse the Person → retain original source attribution → Today becomes actionable again.

  3. 02c

    Hand the relationship to a colleague

    Change stage → reassign to B → B's Today gains the inquiry work and A's loses it → both can still view the Person → reload and inspect history.

  4. 02d

    Recover an uncertain submission

    Lose the response after a real lead submission commits → retry the same form submission → exactly one Inquiry and one set of creation facts exist.

What must be true at the end

Person identity is stable, Inquiries remain distinct, and history/derived activity agree with PostgreSQL. Assignment changes Today ownership, not Organization-wide Person visibility. Another Organization sees neither records nor events.

Failure branches and source anchors

Same submission retry versus new submission, ambiguous contact matches, missing contact methods, rejected optimistic stage/assignment changes, and another remaining Today reason.

03
Controlled external input

Inbound lead routing and unresolved recovery

Routing settings, incoming source data and recovery of unresolved payloads form one intake lifecycle.

WhoOrganization admin and the routing pool of agents.

Starting stateAn operational Organization, an intake address, and synthetic inbound messages.

  1. 03a

    Route unattended leads

    Admin selects default assignee → submit synthetic mail at the real inbound endpoint → routed lead appears on the agent's Today; repeat with unassigned mode → People contains the lead without inquiry work on an agent's Today.

  2. 03b

    Maintain round-robin continuity

    Enable round-robin → receive successive new leads → deactivate a pool member → rotation skips them → reactivate and continue from the retained position; an explicit assignment does not consume a turn.

  3. 03c

    Resolve failed extraction

    Receive unmatched or invalid mail → metadata appears in Unresolved → admin opens raw content and retries → qualified extraction creates the lead once; use a separate payload to exercise discard.

What must be true at the end

Raw payload is preserved encrypted; routing facts explain actual outcomes; processing retries do not duplicate business records; ordinary members cannot open raw unresolved content or retry/discard it.

Failure branches and source anchors

Direct versus forwarded mail, low-confidence/invalid extraction, inactive default assignee, invalid intake address, worker interruption, and duplicate delivery according to the intake contract.

Controlled external input

Captured correspondence and reply follow-up

Outbound capture, inbound replies and held mail change the same relationship's timeline and response state.

WhoAttributed agent, another member, and a synthetic correspondent.

Starting stateAn agent capture address and a Person with a matching email contact.

  1. 04a

    Follow an email exchange

    Deliver synthetic outbound CC/BCC mail → capture metadata and email contact attempt appear → inquiry work clears → deliver an inbound reply → Today shows client-replied work → capture the next outbound response.

  2. 04b

    Recover missed correspondence

    Forward an older message → timeline places it at its original time → re-forward it → no duplicate entry and no backward movement of activity maxima.

  3. 04c

    Resolve held correspondence

    Deliver unmatched correspondence → attributed agent sees a held row → link to an existing Person or dismiss a separate row → rotate the capture address → old address no longer captures correspondence.

What must be true at the end

Metadata is visible Organization-wide, held rows remain attributed-agent-only, and raw correspondence has no read surface. Capture never silently creates a Person or enters the lead-extraction pipeline.

Failure branches and source anchors

Other-member/admin held-queue denial, reply-all versus mail that never reaches capture, deduplication, forwarded dates, and stale link/rotation attempts.

05
Core stack

Relationship notes, tags, and custom fields

Agents build shared relationship context on one record, with different ownership rules for each edit.

WhoAuthor/member A, member B and an Organization admin.

Starting stateA visible operational Person and custom-field definitions created through the admin surface or setup commands.

  1. 05a

    Collaborate on notes

    A adds a note → B sees it on the Person timeline → A edits → admin can edit/delete → deleted text disappears after reload and in another session.

  2. 05b

    Organize a Person

    Create/apply a tag → another member applies the same normalized name without a duplicate definition → remove the Person link → exercise creator permissions while unused and admin-only management once used.

  3. 05c

    Maintain typed values

    Admin creates text, number, date and choice fields → member sets and edits values → another session reads them → clear a value → archive/restore a definition or option while preserving stored values.

What must be true at the end

Note and field content lives in erasable CRUD, not immutable facts or realtime payloads. Note tombstones clear bodies. Person tag/value changes propagate through real invalidations; catalog changes follow their existing refetch behavior.

Failure branches and source anchors

Non-author note edit denial, invalid typed values, wrong-Organization IDs, archived field versus archived option behavior, stale catalog choices, and rejected writes not leaving optimistic success.

06
Core stack

Task follow-up from creation to completion

The task row, Person timeline and Today panel are three views of the same follow-up lifecycle.

WhoTask creator, task assignee, unrelated member and admin.

Starting stateA Person with independently controlled inquiry/list reasons; task due times comfortably inside or outside each window.

  1. 06a

    Complete and reopen work

    Create a task assigned to B → B sees it on Today when due → complete from Today → Person history shows completion → reopen from the Person page → work returns.

  2. 06b

    Reschedule and transfer work

    Snooze an open task → verify the new due instant and resulting eligibility → edit/reassign it → new assignee owns the task work → delete → no active or completed task content remains in reads.

  3. 06c

    Separate task ownership from Person ownership

    Assign the Person to A and a due task to B → B gets task work → complete it while another reason remains → only the task reason clears.

What must be true at the end

Task state is durable; completion history is a projection of that row, so reopening removes it. Complete/reopen/snooze obey target-state idempotency. Today task ownership follows the task assignee; authorized managers are creator, assignee or admin.

Failure branches and source anchors

No due date, date-only local end-of-day conversion, overdue versus due-soon, unrelated-member write denial, completed-task snooze, deactivated assignee, and delete tombstone. Snoozing to tomorrow need not exit the rolling 24-hour window.

Core stack

Saved lists and configurable Today work

A saved definition controls discovery and can also supply ongoing work; edits and broken references affect both surfaces.

WhoPersonal-list owner, another agent and an Organization admin.

Starting stateA small known book spanning stages, assignments, tags, activity and custom-field values.

  1. 07a

    Build a personal work source

    Filter People → preview results → save personal list with sort → reopen → enable as a Today source → change a Person so membership changes → observe list, count and Today reason.

  2. 07b

    Share criteria without sharing private definitions

    Admin creates a shared list → agent opens and duplicates it → agent edits their copy → admin cannot discover the agent's personal definition; each viewer resolves 'me' to themselves.

  3. 07c

    Repair a broken source

    Delete a referenced tag or archive a referenced field → list remains repairable and Today reports unavailable source while other work remains → repair/restore → membership returns → delete the list and verify source preference cleanup.

  4. 07d

    Tune built-in work

    Admin previews a Today rule for a selected agent → saves → agent gets the revised deterministic reasons → disable/revert → default behavior returns; the fixed task axis remains outside these controls.

What must be true at the end

Saved criteria and sort persist; unsaved preview edits do not change Today. Overlapping sources yield one Person with the correct reasons. Contact clears only reasons whose predicates stop matching. Personal definitions stay private even from admins.

Failure branches and source anchors

Five-source limit, stale revisions, archived options remain valid filter choices, stale-reference versus genuine empty result, and keeping all usable work when one source fails.

Controlled inference

Operator-assisted CRM work

The conversation proposes or requests work, while normal application commands and receipts determine what actually happened.

WhoSigned-in agent with server-owned permissions and a deterministic inference provider.

Starting statePeople, saved lists and tasks created through normal commands; inference scripted at the provider boundary.

  1. 08a

    Find and explain work

    Ask for People/list results and why a Person is on Today → approved tools retrieve current authorized data → follow a returned Person link and compare with the conventional UI.

  2. 08b

    Create only after confirmation

    Ask to create a task → inspect proposal → verify no task yet → dismiss; repeat and confirm → exactly one task appears on the Person and appropriate Today view.

  3. 08c

    Complete with Undo

    Ask to complete a task the Operator has resolved → server receipt shows completion → another view observes it → click Undo → task reopens through the normal command.

What must be true at the end

Read answers and mutations use the same application paths as the Web UI; proposal/receipt data is server supplied. Audit rows contain permitted metadata, not conversation text. Business effects persist across reload even though session-only cards do not.

Failure branches and source anchors

Ambiguous names, cross-Organization/private-list requests, malicious note content, inference timeout/failure, denied task completion, changed authorization at confirmation, and uncertain confirm response. Operator call confirmation joins family 09.

09
Telephony integration

Browser call and required outcome

Dialing, provider lifecycle, automatic contact evidence and the human outcome must remain one coherent call.

WhoCaller, a different Person assignee, and a controlled call recipient/provider.

Starting stateCallable synthetic Person and an isolated telephony test environment.

  1. 09a

    Finish a call

    Click Call → browser joins → call rings/answers → end call → automatic contact evidence exists → required outcome remains on caller's Today → choose outcome → timeline and Today settle.

  2. 09b

    Recover interrupted calling

    Exercise busy/no-answer, cancel before ringing, microphone denial or provider failure → preserve the correct contact-attempt/no-attempt distinction → reload and recover authoritative call state or outstanding outcome.

  3. 09c

    Confirm an Operator call

    Ask to call the Person → server-backed proposal → cancel or confirm → confirmation uses the same call lifecycle → repeat delivery/confirmation cannot create a second call where the existing contract deduplicates it.

What must be true at the end

Only the caller controls the call; org members may read it. An automatic attempt exists only for qualifying transitions. Human outcomes append correction facts; an unresolved outcome belongs to the caller, even when someone else owns the Person.

Failure branches and source anchors

One active call per user, repeated/out-of-order provider events, correction chain, session/access loss, and separate evidence for signaling/state versus actual audio transport.

10
Controlled FUB source

Migration from source evidence to reviewed CRM state

Migration is its own long-lived state machine; imported data remains under review rather than entering normal operational work.

WhoMigration admin, ordinary member and another Organization's admin.

Starting stateA new empty destination plus versioned synthetic FUB books; separate fixtures for original, admitted and recovered cohorts.

  1. 10a

    Assess and retain source evidence

    Save a connection → bounded assessment → capture core/history evidence → inspect coverage and exclusions → pause/cancel/resume or retry → reload durable reports. Assessment success is not full capture or migration completeness.

  2. 10b

    Import core People into review

    Map stages and agents → inspect immutable preview → confirm exact plan → review imported People, provenance and reconciliation → prove overlapping contacts did not merge distinct source People and the workspace is held.

  3. 10c

    Add dependent families

    Import tags/fields, notes/tasks and historical metadata for eligible original/admitted/recovered People → inspect paged Person review → verify mappings, explicit date-only timezone, preserved source evidence and no native contact credit from imported history.

  4. 10d

    Refresh, repair and recover

    Capture a later source → compare → refresh existing People or admit genuinely new People → repair missing mappings → recover proven never-imported People once → prepare combined metadata/activity/history refresh → confirm exact families → cancel one family → prepare and finish the exact remainder.

What must be true at the end

Source identities, frozen plans, successful writes and reconciliation survive reload/retry/restart. Local changes and tombstones stay protected; source absence is not deletion. Confirmed clears/removals, task transitions and append-only history corrections follow 010g1. Every completed run retains the admin review hold.

Failure branches and source anchors

Stale preview, lost confirm response, partial cancellation, budget pause, worker restart, expired compatibility evidence, unknown versus inaccessible coverage, original/admitted/recovered identity overlap, and member/admin operational-action denial while held.

What every family should carry

Shared evidence, inside the journeys

Real realtime

Different agents use separate contexts, one active tab each. Observe the actual WebSocket invalidation and API refetch. A fallback poll must not hide a broken event path.

Recovery after lost delivery

Interrupt only owned test resources, commit through another session, reconnect and recover from API state. Catalog definitions and migration progress retain their actual polling/refetch contracts.

Durable state

Reload or sign in afresh. Read narrowly scoped database assertions for identities, counts, history, tombstones and import results. Setup uses typed commands, not direct business-table writes.

Tenant and role boundaries

Exercise denied UI paths and foreign IDs against the real API. Prove no data, mutation or event crosses Organizations. A platform admin is not a tenant superuser.

Real failures and declared retries

Lose a response after the real request commits, then retry the same identity where supported. Native task creation has no client-minted idempotent create ID; do not assume universal exactly-once behavior.

Honest partial results

Distinguish empty, unavailable, held, cancelled and complete. Clearing one Today reason may leave another. Settling a migration run does not prove full source coverage.

Keep the application stack real; control external inputs.Email enters the inbound handler. Scripted inference keeps the real Operator tool loop. Migration Reader fixtures do not prove the live FUB HTTP adapter. Simulated call state does not prove LiveKit/SIP audio. Each result should name the boundary it actually exercised.

Use isolated owned services and build outputs. Keep routine fixtures small. Browser clock changes do not control Rust or PostgreSQL time. Performance and production capacity remain separate under D-050.

Proposed delivery sequence

Build outward from one complete proof

  1. Lead, contact, repeat inquiry and handoff.02a–02c, real realtime recovery, foreign-tenant denial, then 02d lost-response retry.
  2. Daily follow-up and relationship context.06 tasks, 05a notes and 07a saved-list work sources.
  3. Access and Organization controls.01 membership lifecycle; remaining 05/07 catalog, privacy and Today-rule branches.
  4. Assisted and inbound work.08 Operator, 03 inbound intake and 04 correspondence with controlled inputs.
  5. Migration as four smaller workflow families.Start with 10b review hold, then 10a capture, 10c dependent imports and 10d refresh/recovery. Reuse the existing 010g1 browser acceptance.
  6. Telephony in its own integration lane.09 distinguishes call-state coverage from real media-path coverage.

Activation/cutover, outbound messaging, recordings, inbound/multi-device calls, chat, Deals, calendar sync, autonomous outreach and Person erasure need their owning specifications.
