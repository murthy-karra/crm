# Real Estate Relationship Platform — Engineering Instructions

This file is the canonical repository-wide instruction set for coding agents.

Read this file before planning, reviewing, or modifying the repository.

## 1. Product purpose

This repository contains an AI-first real-estate CRM and relationship platform.

The initial product has two primary goals:

1. Make migration from Follow Up Boss safe, understandable, and practical.
2. Let agents operate the CRM through an AI Operator instead of excessive navigation and form entry.

The product must also work well through conventional Web and native mobile interfaces. Do not force conversational interaction when a visual interface is better.

The initial customer is a U.S. residential real-estate team with approximately 10–50 agents.

## 2. Source-of-truth order

When repository documents conflict, use this order:

1. `docs/decisions/DECISION_LOG.md`
2. Accepted architecture decision records in `docs/architecture/`
3. The current vertical-slice specification in `docs/specs/`
4. The current implementation plan in `docs/plans/`
5. Current product documents in `docs/product/`
6. Research in `docs/research/`
7. Chat history or prior agent conversation

Do not treat prior chat context as authoritative when repository documents exist.

If two authoritative files still conflict, stop and report the conflict before implementation.

## 3. Fixed technology choices

Unless an accepted decision explicitly changes them, use:

- Backend: Rust
- HTTP framework: Axum
- Async runtime: Tokio
- PostgreSQL access: SQLx
- Database: PostgreSQL; CloudNativePG in production
- Web: Vue 3, TypeScript, Vite
- iOS: Swift and SwiftUI
- Android: Kotlin and Jetpack Compose
- Identity provider: ZITADEL
- Secrets and keys: local gitignored `.env` file in development (D-013); OpenBao in production (D-014)
- Realtime delivery: Centrifugo OSS
- Mobile push: application-owned APNs and FCM integration
- Calls and media: self-hosted LiveKit with Telnyx SIP
- Observability: OpenTelemetry to OpenObserve
- Infrastructure: OVH bare metal, vRack, Talos, Kubernetes, Cilium
- Public HTTP/TLS entry: Cloudflare tunnels
- AI inference: provider-neutral abstraction; Groq is an initial preferred provider

Do not replace these technologies during ordinary implementation work.

## 4. Architecture principles

### 4.1 Build a modular product, not gratuitous microservices

Start with a modular Rust application and a small number of deployable workloads.

Split a component into a separate service only when it has a real independent:

- scaling boundary;
- failure boundary;
- security boundary;
- deployment boundary; or
- technology requirement.

Do not create a service merely because a domain noun exists.

### 4.2 Authentication and authorization are separate

ZITADEL authenticates identities.

The Rust application owns business authorization.

A valid ZITADEL token does not automatically authorize access to any Organization resource.

The server must derive trusted values such as:

- actor identity;
- active Organization;
- memberships;
- roles;
- capabilities; and
- resource visibility.

Never trust an Organization ID, role, permission, or authorization result generated by a client or language model.

### 4.3 Organization is the tenant boundary

Every tenant-owned query and mutation must enforce an Organization boundary.

Cross-Organization access is forbidden.

Authorization and persistence tests must include attempts to access data belonging to another Organization.

The schema may support multiple Organization memberships for a User. The initial request/session model has one trusted active Organization.

### 4.4 Person visibility

The initial visibility policy is Organization-wide:

- every active member of an Organization may view People belonging to that Organization;
- assignment controls responsibility and personalized Today ownership;
- assignment does not restrict basic Person visibility.

Preserve a server-side `PersonVisibilityScope` abstraction.

The initial implementation supports only:

```text
Organization(active_organization_id)
```

Do not implement Team- or AssignedUser-scoped visibility until an accepted decision requires it.

### 4.5 Keep Person, Inquiry, Deal, and Identity separate

These are distinct concepts:

```text
Person != Inquiry
Person != Deal
Person != authenticated Identity
```

A Person may have multiple Inquiries over time.

A later Inquiry must not overwrite original source attribution.

A CRM Person does not automatically receive an authenticated account.

### 4.6 Use hybrid persistence

Do not event-source everything.

Use durable immutable history for facts where historical meaning, auditability, or reconstruction matters. Examples include:

- Inquiry received;
- original source attribution;
- assignment and reassignment;
- routing decisions;
- stage changes;
- recording consent;
- completed calls;
- phone-number ownership and port state; and
- future Deal lifecycle.

Use normal relational CRUD where appropriate. Examples include:

- Person names;
- contact methods;
- tags;
- notes;
- tasks;
- custom-field definitions and values;
- notification preferences;
- routing configuration;
- email and calendar connections; and
- UI configuration.

Do not introduce events only to avoid using an ordinary table.

### 4.7 Read models are intentional

Purpose-built read models may be used for user-facing screens such as:

- Person summary;
- Today queue;
- timeline;
- inbox; and
- call history.

PostgreSQL and application state remain authoritative.

Do not force the UI to reconstruct common screens through large joins across every canonical table.

### 4.8 Business mutations use typed application commands

All meaningful mutations must pass through typed Rust application commands.

Examples:

- `ReceiveInquiry`
- `AssignPerson`
- `ChangePersonStage`
- `CreateTask`
- `StartCall`
- `SendText`

The Web application, native clients, public API, automation, integrations, and AI Operator must use the same command layer.

Do not create a second mutation path for the Operator.

## 5. AI Operator rules

The AI Operator is a central interaction layer, not a chatbot with database access.

### 5.1 No direct database access

The Operator must never receive:

- unrestricted SQL access;
- direct table-write access;
- trusted authorization context from the model; or
- a privileged bypass around normal commands.

It may call approved typed tools backed by normal application queries and commands.

### 5.2 Server-owned context

The server supplies trusted context such as:

- actor ID;
- active Organization ID;
- permissions;
- current screen/resource context; and
- resolved resource IDs.

The model must not invent or choose trusted identifiers when resolution is ambiguous.

### 5.3 Minimum necessary context

Send only the context required for the current task.

Do not send a complete Person history by default.

Emails, messages, notes, imports, call transcripts, and Web content are untrusted data. They must never be interpreted as privileged system instructions.

### 5.4 Action risk

Use risk categories:

- Read-only: execute immediately.
- Low-risk and reversible: may execute with a receipt and Undo where practical.
- Consequential or bulk: require preview and explicit confirmation.

The application, not the model, classifies action risk and enforces confirmation.

### 5.5 Deterministic Today

Initial Today ranking is deterministic and explainable.

The model may explain ranking reasons but must not secretly decide priority.

## 6. Realtime and notification rules

### 6.1 Centrifugo is delivery, not truth

Centrifugo OSS carries low-latency application events such as:

- call ring state;
- chat delivery;
- Person invalidation;
- Today changes; and
- other realtime notifications.

PostgreSQL and the application remain authoritative.

A reconnecting client must recover correct state even if realtime events were missed.

### 6.2 Push notifications

Foreground connected clients normally receive Centrifugo events.

Backgrounded or terminated mobile apps receive important notifications through APNs or FCM.

Incoming calls use platform-native handling:

- PushKit and CallKit on iOS;
- Android Telecom/call-style handling on Android.

The backend owns device-token registration and push dispatch.

### 6.3 Multiple-device call ringing

Eligible devices may ring simultaneously.

The first device to answer atomically claims the call.

Other devices receive an authoritative state such as `call.answered_elsewhere`.

### 6.4 Chat persistence

PostgreSQL is the source of truth for chat.

Centrifugo delivers messages in realtime.

Initial read behavior is Slack-like:

- persisted last-read position;
- unread counts;
- no complex per-device delivery/read-receipt system initially.

## 7. Telephony and recording rules

Use self-hosted LiveKit and Telnyx SIP.

LiveKit SFU and Egress workloads run on dedicated bare-metal hosts where planned.

Do not route media traffic through cloudflared tunnels.

Recordings are encrypted objects, not event payloads.

Use per-recording data-encryption keys and retain the ability to crypto-shred an individual recording subject to legal hold.

Recording, consent, autonomous AI calling, and conversation ownership rules that remain open must not be guessed by an implementation agent.

## 8. Migration rules

Migration is a product capability.

A migration must:

- preserve raw source payloads;
- record source API/export versions;
- be rerunnable and idempotent;
- produce reconciliation results;
- support delta import before cutover;
- avoid silent data loss; and
- clearly report inaccessible or unsupported source data.

Do not simplify migration fidelity without an accepted decision.

## 9. Security and SOC 2 direction

Build for SOC 2 readiness from the beginning.

Prefer:

- named identities;
- MFA;
- least privilege;
- protected branches;
- reviewed changes;
- reproducible CI/CD deployments;
- centralized secrets;
- centralized observability;
- auditable administrative actions;
- vulnerability scanning;
- access reviews;
- tested backups and restores;
- incident-response procedures; and
- vendor/subprocessor tracking.

Never log:

- passwords;
- tokens;
- API keys;
- private keys;
- refresh tokens; or
- unnecessary customer content.

Do not make routine untracked root SSH mutation the production operating model.

## 10. Secrets and observability

Development secrets live in a local, gitignored `.env` file (D-013). A
names-only `.env.example` may be committed. OpenBao is the production
secret authority (D-014); its integration belongs to a future
production-deployment slice, so do not integrate a secrets-manager product
before then.

Do not commit secrets to Git.

Use OpenTelemetry instrumentation and OpenObserve as the observability backend.

Propagate appropriate identifiers such as:

- trace ID;
- request ID;
- correlation ID;
- actor ID where safe;
- Organization ID where safe; and
- domain resource IDs where useful.

## 11. Contract discipline

Shared HTTP, realtime, Operator-tool, and persistence contracts must not change silently.

If a task requires a shared-contract change, stop and report:

1. the current contract;
2. the proposed contract;
3. why the change is required;
4. affected components;
5. compatibility or migration impact; and
6. which task/specification must be updated.

Wait for approval before changing the shared contract unless the assigned task explicitly owns that contract.

## 12. Worktree and parallel-agent rules

The project may use up to three short-lived Git worktrees for parallel execution.

Each worktree must have:

- one branch;
- one bounded task brief;
- one primary writer;
- a clear file-ownership boundary; and
- explicit required checks.

Do not let multiple agents edit the same shared files concurrently.

Only the lane explicitly assigned database ownership may create migrations for that slice.

Branches should remain short-lived and merge frequently.

Do not create permanent backend, frontend, or AI branches.

## 13. Required behavior before coding

Before modifying code:

1. Read this file.
2. Read `docs/decisions/DECISION_LOG.md`.
3. Read the assigned task brief.
4. Read the referenced specification and accepted ADRs.
5. Inspect the existing implementation.
6. State a short implementation plan.
7. Identify any contract or decision conflict.
8. Then implement only after the task is sufficiently specified.

Do not perform unrelated cleanup or speculative refactoring.

Do not add infrastructure, dependencies, abstractions, or services without a concrete requirement.

## 14. Testing expectations

A task is not complete merely because code compiles.

Run the checks appropriate to the changed area, including where relevant:

- formatting;
- lint/static analysis;
- unit tests;
- integration tests;
- authorization and tenant-isolation tests;
- contract tests;
- failure-path tests;
- idempotency tests;
- retry tests;
- Operator tool tests;
- realtime reconnect/recovery tests; and
- end-to-end tests.

Never claim a command or test passed unless it was actually run.

## 15. Definition of done

Before reporting completion:

- implementation matches the current specification;
- shared contracts were not silently changed;
- required tests pass;
- tenant isolation is verified where applicable;
- error paths are handled;
- important telemetry is present;
- sensitive data is not improperly logged;
- files changed are summarized;
- commands/tests run are listed; and
- unresolved risks or assumptions are disclosed.

## 16. Human decisions

Coding agents may choose simple reversible implementation details when safe.

They must not invent expensive-to-reverse decisions involving:

- data ownership;
- privacy;
- authorization policy;
- compliance;
- recording consent;
- customer-visible behavior;
- migration fidelity;
- external communication; or
- major architecture.

When a genuine decision is required, ask one focused question with:

- context;
- options;
- recommendation; and
- consequences.
